# Explanation

My branching strategy:

The strategy that I used was to create a single branch labeled developer-branch. 
This would allow me to make changes to the project without affecting the main branch. Since it was only me
working on the project and it's simple with only a few basic html files, I found one branch to be enough for development.
<br>
<br>
<br>
My commit philosophy:

My goal was to make a commit at development milestones that were reached instead of commiting after
every small change. This way I had good solid commits that reflected major changes to files instead of floooding the commit history
with tons of very small changes. For example, instead of changing a single sentence and commiting, I waited until I was done editing all
the text in whatever file I was working on and then committed all the changes.
<br>
<br>
<br>
How I would improve this repo for a production enviroment:

To prepare for a team working on this project I would add more folders to clean up organization. Being in a team would potientially mean a bigger project 
which would lead to more files and other resources being added to the repo. The structure setup that I have is fine for the small project that I made 
for this assignment, but it would get very confusing to navigate files once more contributions start getting pushed to the repo. I would also consider adding
rulesets and setting up the condition that at least one person must review the changes in a PR before a merge can occur. This would help protect the security and stability of the project
and ensure all contributors are making healthy and safe changes to the project.
